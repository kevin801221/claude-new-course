# 你的工作

產出一份**變更請求**，交給 console-owner。四段照 §12.2 的 (a)(b)(c)(d)，一段都不准少、順序不准換。

🔒 **落筆的只有 console-owner。** 這個指令的 `allowed-tools` 沒有 Write 也沒有 Edit，
但那是**防手滑，不是鎖** —— 同一份 frontmatter 裡還有 `Bash(sed:*)`，一句 `sed -i` 照樣寫得進
`_Context/api-contract.md`；`.claude/hooks/guard-ownership.sh` 的 matcher 只看
`Write|Edit|MultiEdit`，這條路根本不經過它（那支 hook 自己的檔頭就寫了這個繞道）。

真正擋越權的是這兩樣，而且都不在你打字的那一刻擋，是**跑起來**或**驗收時**抓人：

| 機制 | 擋哪一種越權 | 怎麼擋的 |
|---|---|---|
| `/gate` B 段的逐檔對表 | 動到不屬於自己的**檔案**（含契約本身） | `git status --short --untracked-files=all` 拉清單，逐檔對 `_Context/team-roles.md` §1 的擁有權表，越權的檔進驗收表被點名 |
| `src/app/bus.py` 的 `TYPE_OWNERS`（第 41 行起） | 發不屬於自己**前綴**的事件 | `append_event()` 執行時直接丟 `ValueError`（bus.py:129 未知前綴 / :131 不是擁有者），不是靠自律 |

所以你要做的是把請求寫清楚到 console-owner 讀完就能直接落筆的程度 —— 不是因為你改不動，
是因為你改了會在 `/gate` 上被逐檔點名，而且是整合當天才被點名。

## ⛔ 方向鎖：契約與實作不一致時，**契約是對的，改實作**

反過來的那一天（「程式已經這樣寫了所以契約改一下」）就是整合當天爆掉的起點（§12.5 原文）。
先用這張表把方向確認掉，方向錯的請求不要往下寫：

| 你聽到 / 你正想說 | 真正該做的事 | 放行的話炸在哪 |
|---|---|---|
| 「程式已經這樣寫了，契約改一下對齊」 | 改實作 | 契約是五個人唯一的共同地基。它跟著誰的實作跑，另外四位手上那份就全錯了，而且沒有人會收到通知 |
| 「回傳少了一個欄位，先把契約那欄刪掉」 | 補實作把欄位填上 | 前端照契約寫了 render，欄位消失 = 畫面上一個永遠空的格子，沒有人知道那是「沒做」還是「壞了」 |
| 「這個錯誤碼語意不合，先借一個現成的用」 | 走 §12 補一列新碼到 §10 | 值班的人照錯誤碼查錯地方（現成案例：`409 DS_NOT_READY` 借了 `SELFCHECK_FAILED`，症狀跟歸責從此對不上） |
| 「先回假資料，之後再接真的」 | 維持 `501` | 回假資料會讓前端以為自己接好了，真接上那天才發現形狀根本不同 |

**唯一能反過來的情況**：契約寫的東西**物理上做不到**（例：§2 裁決 A —— `EventSource` 只能 GET，
所以 POST 端點在瀏覽器裡訂閱不了）。這時 (b) 段要拿得出那個物理限制本身，不是「比較好寫」。

## 第 0 步：先確認這真的是契約問題

一半的「契約要改」其實是實作 bug，改了契約等於把 bug 寫進共同地基。

| 症狀 | 其實是什麼 | 該做的事 |
|---|---|---|
| 契約有這個欄位，實跑回來永遠 `null` | 實作沒填 | 開工單給那個欄位的擁有者，**不是**變更請求 |
| 契約沒寫，但實作已經在回了 | 越權加欄 | 走 §12 把它補進契約（類型：向後相容加欄），並在 (b) 段老實寫「已在實作中，補正式化」 |
| 前端要顯示的數字後端沒有 | 快照或事件真的缺欄位 | 這才是變更請求（§8.3 加選填欄位的前例就是這樣來的） |
| 端點回 `501` | M6+ 還沒做 | 照里程碑排，不是契約缺陷 |

## 第 1 步：定位節號，並判「加東西 vs 改東西」（§12.3）

| 你的改動 | 類型 | 代價 |
|---|---|---|
| `data` 物件新增**選填**欄位、`rule`/`code`/`reason` 這類 enum **新增值**（含新錯誤碼、新事件 type） | 向後相容 | 通知 + 本檔補一列，仍由 console-owner 落筆 |
| 改欄名、改型別、改語意、刪欄位、改 HTTP 狀態碼 | **破壞式** | 同一個 PR 一起改前端與所有呼叫方，`v` 從 1 進到 2 |

能設計成「加一個選填欄位」就不要設計成「改既有欄位」—— 成本差一個數量級，而且破壞式改動要
連帶動到前端 reducer（§5.4 心跳那次就是：改了框格式，同一個 PR 得在前端加 case 擋掉）。
判成破壞式的話，(c) 段要一併給出 `v:2` 的信封範例。

## 第 2 步：收證據（(b) 段沒證據就退件）

全部唯讀，可以直接跑：

| 要什麼 | 指令 |
|---|---|
| 契約原文（引用用） | `sed -n '<起>,<迄>p' _Context/api-contract.md` |
| 實作現況 | `grep -rn "<欄位/type/錯誤碼>" src/ scripts/ prototype/index.html` |
| 真的發生過的事件 | `jq -c 'select(.type=="<type>") \| .data' runs/<run_id>/events.jsonl \| head -3` |
| 帳本現況 | `tail -3 runs/runs.jsonl` |

(b) 段要有其中一樣：**真的跑過的呼叫**、**真的看到的錯誤字串**、或**畫面上真的錯的那個數字**，
並附檔案行號。「以後可能會需要」不算證據 —— 那會讓契約長出沒有人用的欄位，而每個沒人用的欄位
都是另外四個人要跟著維護的謊。

## 第 3 步：(c) 寫完整 JSON，不是 diff 片段

- 事件就給**一整包信封**（`v` `seq` `ts` `run_id` `stage` `type` `actor` `data` `text` 全帶），
  不要只寫 `data` 裡多的那一欄 —— console-owner 要能直接貼進 §4 當範例。
- 型別寫死（`int` / `float` / `string[]` / `null`），別寫「數字」。
- 單位照 §1 寫在欄名尾：時間 `_s`/`_min`、記憶體 `_mb`、金額 `_usd`。bbox 一律
  `cx,cy,w,h` 正規化到 `[0,1]`。
- 錯誤就給 `{"code":"<MACHINE_CODE>","detail":"<繁中一句話>"}`，並寫明 HTTP 狀態碼。

---

## 第 4 步：(d) 誰要跟著改

| 你在改什麼 | 一定要一起改的 | 為什麼漏了會出事 |
|---|---|---|
| 新事件 `type` | §4 type 表加一列 + `src/app/bus.py` 的 `TYPE_OWNERS`（第 41 行起）+ 發它的那支 router + `prototype/index.html` 的 `switch (ev.type)`（第 1250 行起） | 前綴不在 `TYPE_OWNERS` 裡，`append_event()` 當場 `ValueError` 擋下（bus.py:129）；前端沒有 `case` 則是**靜默丟掉**，比報錯難查 |
| 新錯誤碼 | §10 錯誤碼表加一列 + raise 它的那支 router（各檔的 `_err()` helper） | 契約沒有的 code 前端只會印原字串；而 §10 是值班的人唯一的查表處。前端通常**不用**改：只有一套錯誤渲染器 `showErr()`（`prototype/index.html:508`），吃 `{code, detail}` 不做 per-code 分支 |
| REST 形狀（body / 回應 / 狀態碼） | §8 對應小節 + 該 router + 前端 fetch 那段 + `scripts/selfcheck.py`・`scripts/run_all.py` | 會產生事件的 POST 一律 `202` + JSON（§1），改成串流會撞上「全系統只有一條 SSE 出口」 |
| 事件 `data` 加欄 | §4 那一列 + 發它的 router + 前端 case；快照也要回的話再加 §8.3 | 前端不准自己算數字（側欄說謊那次就是前端自算的），要顯示就得有人在快照裡給 |
| stage 代號 / 順序 | §3 + §8.10 `GET /stages` + 前端 rail | 11 格在 M0 就定死是為了讓前端只寫一次版面，加減格版面會跳 |

每一列都要標**擁有者**（照 `_Context/team-roles.md`）與**里程碑**（M2 / M5 / M6…）。
沒標里程碑的請求 = 沒有人知道現在到底該不該動手，它會躺在那裡直到整合當天。

## 交出去之後

請求交給 console-owner（Kevin）。在他落筆之前：

- **不要先改實作「等契約跟上」** —— 那就是 §12.5 點名的那個方向，而且一旦程式先跑了，
  討論就會變成「要不要為了改契約重寫程式」，答案永遠是不要。
- **不要先在自己的 router 回新欄位當「做一半」** —— 前端會以為接好了。
- 被否決是正常結果。否決通常代表這件事該用既有形狀做，或該排到後面的里程碑。
